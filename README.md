# rvjit integration: reproducible evaluation

Scripts and inputs to evaluate the oneDNN pull request that generates the RV64
brgemm, GEMM and 1x1-convolution kernels with
[rvjit](https://github.com/alexandrelimassantana/rvjit) (RFC
[uxlfoundation/oneDNN#5532](https://github.com/uxlfoundation/oneDNN/pull/5532)). They do the following:
- build oneDNN before and after the PR;
- check both for correctness and time them on an RV64 machine with oneDNN's
  benchdnn;
- turn the logs into CSVs, a performance-CI report and plots.

The PR author's results come from a BananaPi F3 (SpacemiT K1, RVV 1.0, VLEN 256)
and are in [`evaluations/bananapi-f3.md`](evaluations/bananapi-f3.md).
Reviewers are expected to run the same scripts on their own RV64 hardware and
compare their `csv/report.md` with it.

```
versions.conf      the two versions: oneDNN at the PR's base, and the PR
container/         cross-compiler image (GCC 14, as oneDNN's RISC-V CI) and its toolchain file
scripts/           fetch, build, run (the five tasks), report (one per job), slurm
inputs/<task>/     the benchdnn batches of each task (correctness-onednn/, correctness-extended/,
                   performance-onednn/, performance-extended/)
inputs/common/     the warm-up batches
analysis/          collect.py, compare.py, perfci_report.py, plots.py
evaluations/       reference results: <machine>.md (report.md) and its figures
```

Generated, not versioned: `sources/` (checkouts), `build/`, `install/` (what
the RV64 machine needs), `results/` (logs), `csv/`, `figures/`.

## Quick start

```bash
git clone https://github.com/alexandrelimassantana/reproduce-rvjit-onednn-integration.git
cd reproduce-rvjit-onednn-integration

# 1. Build both versions (any Linux machine; see "Build" for the toolchains)
scripts/build.sh

# 2. On the RV64 machine (copy install/, inputs/ and scripts/ there unless built on it)
rsync -a install inputs scripts versions.conf board:rvjit-repro/
ssh board 'cd rvjit-repro && scripts/slurm/submit.sh --partition P run'   # all checks: 24 jobs (or scripts/run.sh without slurm)

# 3. Back on any machine with Python 3
rsync -a board:rvjit-repro/results/ results/
pip install -r analysis/requirements.txt
analysis/collect.py && analysis/compare.py && analysis/perfci_report.py && analysis/plots.py
# job reports: results/<machine>/reports/; summaries: csv/report.md; figures: figures/<machine>/
# compare csv/report.md with evaluations/bananapi-f3.md
```

### What the PR changes

| Part | What changes | Impls touched (benchdnn name) |
|---|---|---|
| [third-party](https://github.com/alexandrelimassantana/oneDNN/compare/d3f8eb8416caa2ec0e546668a6336a054b9154d4...529426c7250e24a518ced15ca7332677963c7762) | vendors rvjit v0.1.0 and adds `rvjit_matmul.hpp`; no kernel changes | none |
| [brgemm](https://github.com/alexandrelimassantana/oneDNN/compare/529426c7250e24a518ced15ca7332677963c7762...f20711fd873a5e47332b3f447ac915c1d827ab98) | brgemm kernel generated by rvjit (f32, bf16, f16 incl. f16 dst, int8 s32); weights left as `any` are blocked by the tuned M tile and read in place | `brgemm:rvv*` matmul, inner product, conv |
| [gemm](https://github.com/alexandrelimassantana/oneDNN/compare/f20711fd873a5e47332b3f447ac915c1d827ab98...4deafb62d2336d5c4fae65569c21e1b2d537445b) | gemm f32/f16/s8 micro-kernels generated by rvjit; matmul `any` weights pre-packed into panels; new thread partition | `jit:rvv*` matmul; `gemm:rvv` IP and conv (they call the rv64 sgemm) |
| [conv-1x1](https://github.com/alexandrelimassantana/oneDNN/compare/4deafb62d2336d5c4fae65569c21e1b2d537445b...07f60d9f29dbc75101f4c52f355f0a901ae2f83c) | 1x1 conv on rvjit; weights blocked by the tuned OC block; fixed `Oihw{4..32}o` user tags no longer accepted | `jit_1x1:rvv*` |

The PR changes only the following. Every other dispatch condition (shapes,
data types, attributes, thread count) is upstream's.

- **All parts**: the kernels' blocks are tuned by rvjit per VLEN, data type
  and problem instead of being fixed by VLEN. A problem rvjit cannot tune is
  declined (`unimplemented`), and the next implementation runs it.
- **brgemm**: weights tagged with `any` produce blocked layouts tiled by `M`.
  - Inner product: `Ab<m>a` (`ba` when OC < m). Its MB/OC cache guards now
    apply to plain weights only.
  - Convolution: `Ohwi<m>o` / `gOhwi<m>o` (`hwio` / `ghwio` when OC < m).
  - Matmul (f32, bf16, f16): N blocked by the tile and read in place instead
    of packed per tile at execution. int8 weights are still packed.
- **gemm**:
  - `jit:rvv` matmul: weights left as `any` are pre-packed into the kernel's
    panels and read in place; column-major (`ba`) user weights are copied into
    the workspace; the threads split over whole panels.
  - `gemm:rvv` inner product and convolution: the sgemm they call shares one
    kernel per configuration, tuned and generated on first use.
- **conv-1x1**: the OC block and the spatial step come from rvjit. Weights left
  as `any` are `(g)Oi[d]hw<m>o`. User weights in a fixed `Oihw{4..32}o` tag
  are declined unless they equal the tuned layout.

### The five tasks

Every task runs both builds with `$THREADS` threads (default 8). It is split
into jobs, and each job is one slurm job with its own report. The jobs run,
and are submitted, in the order below: performance first.

| Task | Method | Datasets | Jobs |
|---|---|---|---|
| `performance-onednn` | oneDNN's performance-CI method | oneDNN's model shapes: the perf-CI inputs plus ResNet-50 and BERT | 5, one per dataset and primitive: `matmul.nightly`, `matmul.models`, `ip.models`, `conv.nightly`, `conv.models` |
| `performance-extended` | benchdnn `--mode=P`, 25 runs per problem | the IPDPS'26 convolutions and matmuls that reach the changed implementations | 3, one per dataset: `conv.ipdps26`, `conv.ipdps26_1x1`, `matmul.ipdps26` |
| `ctest` | oneDNN's ctest: the API gtests of these primitives | the gtests of matmul, the sgemm, the inner product and the convolution | 8, one per test |
| `correctness-onednn` | benchdnn `--mode=C` against its reference | oneDNN's CI batches of the inner product and convolution (inference), and its CI shapes swept over the PR's data types, weight layouts and attributes | 5: `matmul.ci`, `ip.ci`, `conv.ci`, `ip.test_ci`, `conv.test_ci` |
| `correctness-extended` | benchdnn `--mode=C` | smoke tests: small problems at the edges of the PR's dispatch and layouts | 3, one per primitive: `matmul.smoke`, `ip.smoke`, `conv.smoke` |

- **Inference only.** The builds have oneDNN's inference workload, so every
  task runs forward problems only.
- **Correctness.** A failed problem or a crash makes `run.sh` exit nonzero.
  Each log ends with benchdnn's implementation statistics, which the report
  and `dispatch.csv` show.
- **Performance-CI method** ([`.github/automation/performance`](https://github.com/uxlfoundation/oneDNN/tree/d3f8eb8416caa2ec0e546668a6336a054b9154d4/.github/automation/performance)):
  - each batch is repeated `REPS` times (default 10; the CI uses 50),
    alternating between the two builds;
  - each repetition is a fresh process with `--max-ms-per-prb=300`;
  - `perfci_report.py` applies the CI's t-test to execution and creation
    times.
- **Both performance tasks** record the implementation, GFLOPS, time and
  creation time of every problem.
- **Job reports.** After each job, `scripts/report.py` (Python 3 only, no
  package; skipped if the machine has no `python3`) writes
  `results/<machine>/reports/<task>.<batch>.md`:
  - a ctest test: the result of each build, and whether they agree;
  - a correctness batch: benchdnn's counts per build and data type, the
    implementations each build ran, and the repro lines of failed problems;
    problems whose data type the CPU lacks count as skipped;
  - a performance dataset: rvjit's speedup over all problems, per data type
    and weights tag, and per implementation, plus the slowest problems; one
    row per problem goes to `<task>.<batch>.csv`. Problems a build skipped are
    counted apart and left out of the summaries.

**Warm-up.** The first problem of every benchdnn process pays one-time costs:
loading the library, rvjit's first use, and kernels shared between problems
that are generated on first use. Every performance process therefore first
runs `inputs/common/warmup.<driver>`, a few small problems named `warmup:*`,
on both builds. The reports and the analysis drop them. The creation time
that remains is the per-problem cost, rvjit's tuning and code generation; it
is real and is reported, as `ctime`.

### Datasets

- Batches reference oneDNN's shapes by name. benchdnn finds them in the
  install's `tests/benchdnn/inputs/<driver>/`
  ([source](https://github.com/alexandrelimassantana/oneDNN/tree/07f60d9f29dbc75101f4c52f355f0a901ae2f83c/tests/benchdnn/inputs)).
- Each batch starts with a comment giving its origin and the implementations
  it targets. It sets its own data types, or lists the ones to sweep on a
  `# dt:` line.
- In the snippets, `scripts/run.sh` runs on the RV64 machine itself, and
  `submit.sh` sends the same jobs to slurm (`<P>` is your partition).

## Build

`scripts/build.sh [options] [upstream|rvjit|all]` fetches the pinned commits
when missing (`scripts/fetch.sh`, shallow, into `sources/`) and builds them.
The build uses oneDNN's CMake with OpenMP, RV64, inference only, matmul,
inner product, convolution and reorder, plus benchdnn and the gtests. Each
version is packaged into `install/<name>`. The toolchain is, first match
wins:

| How | Selected by |
|---|---|
| the host compilers | `--native`, or running on an RV64 machine |
| a CMake toolchain file of yours | `--toolchain FILE` |
| your cross compilers | `CC` and `CXX` set (and optionally `RISCV_SYSROOT`) |
| a container image | `--image IMG`, else the default `rvjit-repro:gcc14`, built from `container/Containerfile` (Ubuntu 24.04, GCC 14) on first use with podman or docker (`CONTAINER=`) |

`install/<name>/REVISION` records the commit and the vendored rvjit (release tag and commit).
`install/<name>/BUILD` records the toolchain, compiler, image, library size
and the time of each step.

## Run

On the RV64 machine, from the repository root, one command runs all checks,
the 24 jobs of the five tasks, performance first:

```bash
scripts/slurm/submit.sh --partition <P> run    # with slurm: 24 independent jobs, 3 h limit each
scripts/run.sh                                 # without slurm: the 24 jobs one after another
```

Each job writes its report to `results/<machine>/reports/`; see "Datasets"
for one task or job at a time. Other options:

```bash
THREADS=4 REPS=50 scripts/run.sh performance-onednn          # thread count, perf-CI repetitions
scripts/slurm/submit.sh --partition <P> --time 04:00:00 run performance-onednn --only conv.nightly
DRY_RUN=1 scripts/slurm/submit.sh --partition <P> run       # print the sbatch lines
scripts/run.sh --list                                       # the jobs: "<task> <batch or test>"
```

The job scripts (`ctest.sh`, `correctness.sh`, `performance.sh`, `perfci.sh`)
run on their own too; see `--help` on each.

With slurm, each job runs on an exclusive node, so a failed or timed-out job
does not stop the others. The partition has no default. `THREADS` becomes
each job's thread count, and each job logs to
`results/slurm/<task>.<batch or test>-<job>.out`, its report at the end.
Results go to `results/<machine>/<flavor>/<method>/` (`ctest`,
`correctness`, `perfci`, `perf`), where `<machine>` is the slurm partition,
else the host name. Each log is named `<id>.<driver>.<dt>.t<threads>`, the id
being `onednn-` or `extended-` and the batch (e.g. `onednn-conv-ci`); a
ctest test logs to `<test>.log` and `<test>.result`. A `run.env` records:
- the host;
- the revision;
- `/proc/cpuinfo`'s ISA string and CPU model;
- the thread count.

## Timing

Every script, and every slurm job, appends the duration of each phase to
`results/<machine>/timings.csv`:
- fetch;
- image;
- configure, compile and package for each version;
- every ctest test;
- every batch × data type of every task;
- the whole `run`.

Each script ends with a per-phase total. `collect.py` gathers the files and
`plots.py` draws `timings.png`.

The cost of the dependency is in the build: `install/*/BUILD` records the
library size and build times. Measured times, to estimate yours.
`libdnnl.so` is 10,124,832 bytes for upstream and 10,310,040 for rvjit
(+185 KB, +1.8%):

| Phase | Machine | Time |
|---|---|---|
| fetch (both versions, shallow) | workstation | 5 s |
| image (first build) | workstation | 24 s |
| configure + compile + package, upstream | workstation (4 cores, `-j 4`), container | 14 min (compile 858 s) |
| configure + compile + package, rvjit | workstation (4 cores, `-j 4`), container | 15 min (compile 895 s) |
| the five tasks, 24 jobs | BananaPi F3, 8 threads | 2 h 46 min one after another; 67 min with a node per job |

The 24 jobs on the BananaPi F3 (8 threads, one exclusive node per job), from
start to end of each slurm job, both builds included:

| Task | Job | Time |
|---|---|---|
| performance-onednn | `conv.models` | 1.8 min |
| | `conv.nightly` | 30.8 min |
| | `ip.models` | 10.2 min |
| | `matmul.models` | 0.5 min (bf16 only, skipped on the board) |
| | `matmul.nightly` | 6.7 min |
| performance-extended | `conv.ipdps26` | 1.4 min |
| | `conv.ipdps26_1x1` | 0.6 min |
| | `matmul.ipdps26` | 10.5 min |
| ctest | 8 tests | 4.8 min in all (`test_convolution_eltwise_forward_f32` the longest, 1.9 min) |
| correctness-onednn | `conv.ci` | 3.2 min |
| | `conv.test_ci` | 8.7 min |
| | `ip.ci` | 5.5 min |
| | `ip.test_ci` | 67.0 min |
| | `matmul.ci` | 13.9 min |
| correctness-extended | 3 smoke jobs | 0.6 min in all |
| **total** | | **2 h 46 min** (performance 62 min, ctest 5 min, correctness 99 min) |

- The board skips every bf16 problem (no Zvfbfwma). A CPU that runs bf16
  takes longer, most of all on `performance-onednn.matmul.models` and on
  the bf16 parts of the other batches.
- The time grows with the slower build: rvjit's primitive creation, which
  tunes and generates the kernels, is 1-9x upstream's (see the evaluation).
- The 3 h slurm limit leaves room for the longest job, `ip.test_ci`;
  raise `--time` on slower machines.

## Analysis

On any machine with Python 3, after copying `results/` back:

```bash
pip install -r analysis/requirements.txt
analysis/collect.py [results] [-o csv]   # logs -> csv/{perf,perfci,correctness,dispatch,ctest,timings}.csv
analysis/compare.py [csv]                # -> compare.csv, duplicates.csv, summary_by_{impl,dataset,primitive}.csv, report.md
analysis/perfci_report.py [csv]          # -> perfci_report.csv, perfci_report.md
analysis/plots.py [csv] [-o figures]     # -> figures/<machine>/*.png
```

Performance is reported at three levels, for both performance tasks (a
perf-CI problem counts with the median of its repetitions):

| Level | What | CSV | Figure |
|---|---|---|---|
| comparison | one dataset × data type × weights tag × threads, e.g. `onednn-ip-models f16:f16:f32 wtag=any t8` | `summary_by_impl.csv` | `<comparison>.by_impl.png`, `<comparison>.speedup.png` |
| dataset | one performance batch (`onednn-ip-models`, `extended-conv-ipdps26`, ...), all its data types and tags: a general row over all its problems, then one per implementation | `summary_by_dataset.csv` | `dataset.<id>.png` |
| primitive | the ensemble of every dataset of one primitive (matmul, ip, conv): all problems, per data type, and per rvjit implementation | `summary_by_primitive.csv` | `primitive.<driver>.png` |

- `report.md` is the one-page summary, per machine: the ctest and
  correctness verdicts (each run's counts for both builds and whether
  dispatch changed); the number of unique cases per primitive and the
  repeated ones; then per primitive its `report.<driver>.png` figure and
  performance tables: the ensemble first, then each of its datasets. It
  links the figures in `../figures` (`compare.py --figures DIR` for another
  `plots.py -o`), so run `plots.py` too.
- **Unique cases.** A case is one problem (driver, data type, threads,
  direction, tags, bias, algorithm, attributes and shape, whatever its name)
  run on the same pair of implementations. Datasets share shapes (e.g. the
  ResNet-50 layers of `onednn-conv-models` are also IPDPS'26 convolutions),
  so each table and figure counts a case once: the dataset levels once per
  dataset, the primitive level once per primitive, keeping its first
  dataset. `duplicates.csv` and `report.md` list the repeats with each
  measurement's speedup.
- `report.<driver>.png` has one column per data type: the speedup of
  every case (box plots over all of the primitive's unique cases and per
  dataset), its heatmap over the problem's dimensions, and the heatmap of
  the cases slower than upstream; crosses mark cases on different
  implementations.
- `summary.png` shows the geomean speedup of each primitive's ensemble and
  of each dataset, over all problems.
- Each row has the problem count, the geomean, median, min and max speedup,
  the problems faster, the geomean creation-time ratio, and the geomean
  GFLOPS of each build.
- **Speedup** is rvjit's GFLOPS over upstream's, or upstream's time over
  rvjit's for perf-CI problems (> 1 is faster). The **creation-time ratio**
  is rvjit's over upstream's (< 1 is faster).
- Problems that changed implementation are kept apart (`impl differs`), so
  one implementation's numbers never mix with another's; the `all` rows
  include them.
- `perfci_report.md` is the table to paste into the PR: per dataset, the
  improved, regressed and creation-time-regressed problems by the CI's
  t-test, then the problems that changed.
- Also in `figures/<machine>/`:
  - `<batch>.heatmap.png`: speedup over (M, N, K) for matmul and over
    (OC, IC, spatial) for convolution;
  - `by_impl.png`: every rvjit implementation across every comparison;
  - `impl_overall.png`: per primitive, implementation and data type;
  - `timings.png`.
- [`evaluations/bananapi-f3.md`](evaluations/bananapi-f3.md) is our
  `report.md` from the BananaPi F3, with its figures: the reference to
  compare yours with. Results from other machines are welcome as
  `evaluations/<machine>.md`, produced the same way (`compare.py`, then
  `plots.py`, the report's figures copied next to it).
- `dispatch.csv` lists, per correctness log, the implementations benchdnn
  used, which shows any change of dispatch between the builds; `ctest.csv`
  and `correctness.csv` gather the results the job reports show.

## Limitations

- Results describe the machine they ran on. The kernels' blocks are tuned
  for the machine's VLEN and caches, so other hardware dispatches and
  performs differently. RISC-V CI covers VLEN 128 and 256 under QEMU with its
  SMOKE set only.
- The brgemm matmul dispatches only single-threaded, so the tasks do not
  target it; its data types are listed above for completeness.
- The data types a batch can reach depend on the CPU: f16 needs Zvfh,
  bf16 needs Zvfbfwma.
  benchdnn reports a problem whose data type the CPU lacks as skipped.
- The two builds contain only convolution, matmul, inner product and reorder,
  for inference: backward problems are not run.
